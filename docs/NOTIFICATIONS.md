# FlowTrace 提醒与通知机制汇总

> 本文基于当前工作树（`xcodebuild test` 220 条全部通过）梳理，记录**当前已实现**的行为。
> 需求规范与差距核对的历史记录见
> [.trellis/tasks/09-28-notification-interactions/prd.md](../.trellis/tasks/09-28-notification-interactions/prd.md)
> （已于 2026-10-09 实现完毕，本文即实现后的行为）。
> 所有行为均取自真实代码，出处以「文件 + 机制名」标注；本文不含任何推测。

FlowTrace 里的「提醒」分两层：**应用内提示**（窗口 / 面板里的 UI 元素，不需要系统权限）和
**系统本地通知**（真正的 banner + 声音，需要「系统设置 → 通知 → FlowTrace」的授权）。
两层的行为、去重与关闭方式各不相同，下面逐类说明。

---

## 一、总览

| # | 提醒 | 类型 | 触发前提 | 频率上限 | 关闭方式 |
|---|---|---|---|---|---|
| A1 | 启动引导弹窗 | 应用内模态窗 | 功能开启 + 权限被拒 | 每次启动至多 1 次 | 「不再提醒」永久关闭 |
| A2 | 设置面板内嵌警告 | 应用内 UI 行 | 功能开启 + 权限未给 | 每次进入对应 tab 显示 | 给权限 / 关功能 |
| B1 | 配额阈值通知 | 系统本地通知 | 配额开启 + 跨越阈值 | 80%/自定义：每周期 1 次；100%：增长驱动可重发（可静音） | 关配额开关 |
| B2 | 进程流量异常通知 | 系统本地通知 | 示警开启 + 双条件满足 | 每进程每方向每天 1 次 | 关示警开关 |
| B3 | 保留期提醒通知 | 系统本地通知 | 「提醒手动清理」模式 + 有逾期数据 | 每天 1 次（有逾期则每日重复） | 切自动清理 / 清数据 / 调大保留天数 |

三类系统通知都支持**点击交互**（见第四节）：点通知正文跳转对应界面；配额 100% 通知
额外带三个动作按钮（已知 / 1 小时不再提醒 / 今天不再提醒）。

---

## 二、应用内提示（不需要系统权限）

### A1. 启动引导弹窗

出处：`AppDelegate.swift` → `requestNotificationAuthorizationIfNeeded()` +
`presentLaunchReminderIfNotSuppressed()`

**何时出现**：应用启动时，同时满足：

1. 至少一个会发通知的功能是开启的（配额示警 / 进程流量示警 / 存储清理的「提醒手动清理」）；
2. 系统通知权限处于 **`.denied`（被拒绝）** 状态。

（权限是 `.notDetermined` 时走的是系统授权对话框，不弹这个窗。）

**内容**：说明哪些通知无法送达，提供两个按钮：

| 按钮 | 行为 | 后续还会弹吗 |
|---|---|---|
| 打开系统设置 | 跳转「系统设置 → 通知 → FlowTrace」，**不写任何标记** | 下次启动**仍会弹** |
| 不再提醒 | 向 UserDefaults 写入 `notificationLaunchReminderSuppressed = true` | **永久不再弹** |

**回答「关闭后会一直提醒吗」**：点了「不再提醒」就是永久关闭这个启动弹窗——判断逻辑是
`guard !defaults.bool(forKey: launchReminderSuppressedKey)`，没有任何过期或重置路径
（除非删除应用数据）。唯一例外：XCTest 环境下（跑单元测试时）这个弹窗被环境守卫跳过，
永不出现——模态弹窗会卡死测试套件，这是 2026-09-23 实测后加的守卫。

### A2. 设置面板内嵌橙色警告

出处：`SettingsComponents.swift` → `NotificationPermissionWarning`；
`SettingsQuotaPane / SettingsAlertsPane / SettingsStoragePane` 三处使用。

**何时显示**：对应 tab 内、且该 tab 的通知功能已开启时：

| 所在面板 | 显示前提 |
|---|---|
| 配额 | 「启用配额提醒」开着 |
| 示警 | 「启用进程流量示警」开着 |
| 存储 | 清理方式 = 「通知提醒手动清理」 |

且系统权限处于：

- `.denied` → 橙色警告 + **「打开系统设置」**链接按钮；
- `.notDetermined` → 橙色警告 + **「允许通知」**链接按钮（点击弹系统授权对话框）。

**刷新时机**：设置窗口每个 tab 切换都会重建面板，面板 `.onAppear` 时重新查询权限状态，
所以警告总是反映当前真实的授权状态。

**与 A1 的关系（关键）**：A1 的「不再提醒」**只压制启动弹窗，不影响这里的警告**。这是刻意
设计——启动弹窗是打扰性的（所以允许永久关），设置面板警告是修复路径的入口（所以保持常显）：
只要功能开着而权限没给，每次进入对应 tab 都会看到它，直到你给权限或关功能为止。

## 三、系统本地通知（真正弹 banner 的）

三类通知共用同一个投递口 `LocalNotification.deliver`（见第四节），以下只写各自的触发逻辑。

### B1. 配额阈值通知

出处：`QuotaMonitor.swift`

**前提**：设置里「启用配额提醒」开启，且配额限额（GB）> 0。

**阈值集合**：固定 `{80%, 100%}` + 可选自定义阈值（0 < x < 100 时并入），三者各自独立触发。

**周期**：月 / 周 / 日（跟随设置）。周期起始日的 ISO 日期作为去重 key 的根。

**触发规则**（纯函数 `shouldFire`，可单测）：

```
上一观察点的用量百分比 < 阈值  AND  当前用量百分比 ≥ 阈值
```

- 「跨越式」触发：一直在 85% 徘徊不会反复弹 80%；
- 应用启动后的第一次观察只建立基线（`prevPercent == nil`），不触发——避免启动时把
  「早已超 80%」误报为「刚刚跨过 80%」。

**去重与频率**：key = `"<周期起始日>:<阈值>"`（如 `2026-09-01:80`），存 UserDefaults
`quotaFiredKeys`。**每个周期每个阈值至多一条**；周期滚动后旧 key 自然失效，全部阈值重新
武装。设置里的「清除数据」会调 `resetFiredKeys()`，同样让所有阈值重新可触发。

**送达语义**：**送达成功才写 key**。被系统拒绝（权限没给）时不写 key，改记 15 分钟内存退避，
退避到期后的下一次检查重试——所以用户在系统设置里放开权限后，当天就能补上通知。重启后
退避表清空，立即重试一次。

**100% 阈值的特殊语义（增长驱动，区别于 80%/自定义）**：

- 首次跨越 100% 仍走跨越路径（`prev < 100 && current >= 100`，每周期一次），送达成功后
  把「当时已用字节」记为增长基线（UserDefaults `quota100NotifiedPeriod/Bytes`，随周期
  key 一起存储，周期滚动自动重置）；
- 此后每个检查点若满足「已用 ≥ 100% **且** 未静音 **且** 较上次通知再增长 ≥ 配额的 1%」
  （增量 = `limitBytes / 100`，1 GiB 配额即约 10.2 MiB），**再次通知**并把基线推到当前值；
- 通知携带三个动作按钮（category `QUOTA_100`）：
  - **已知**：无静音——把增长基线移到当前用量，只有继续增长才可能再触发；
  - **1 小时不再提醒**：内存静音 1 小时（重启即解除，与 15 分钟投递退避同款哲学）；
  - **今天不再提醒**：持久化今日静音（UserDefaults `quota100MutedDay`），**重启后当天
    仍然静音**，次日零点自动失效；
- 点掉横幅 / 划掉通知不改变任何状态：不涨不重发、持续增长照规则重发。

80% 与自定义阈值不受以上影响，保持「每周期一次」。

### B2. 进程流量异常通知

出处：`ProcessAlertMonitor.swift`

**前提**：设置里「启用进程流量示警」开启。

**触发规则**（纯函数 `decide`，**AND** 逻辑，上下行各自独立判断）：

```
该进程今日累计流量 ≥ 该方向的 MB 下限
AND
（今日流量 ≥ 该进程 7 日日中位数 × 倍数  OR  基线为 0）
```

- 基线 = 此前 7 个完整自然日（不含今天）的中位数，缺天记 0；
- 基线为 0（新装的进程 / 多日未动的进程）视为「任何流量都异常」，此时仅受 MB 下限约束；
- 下行、上行各有独立的「MB 下限」和「倍数」设置。

**检查频率**：nettop 每秒的帧持续累加今日字节，但**每 60 秒才评估一次**（MB 量级的下限
不值得逐帧评估）。

**去重与频率**：`process_alert` 表的唯一索引 `(day, name_key, direction)`——
**每进程、每方向、每个本地日至多一条**，且这条去重随数据库持久化，重启也不会重发。
投递前还会先查库预检当天名额（唯一索引只保证表干净，拦不住通知本身——2026-10 修复：
同日同方向曾连发 4 条）。触发的通知同时落库为示警记录，即历史窗口「示警日志」栏的来源。

**送达语义**：预检通过后**先投递、成功后才写去重行**（顺序刻意如此——反过来会让
「投递被拒」也占掉当天的唯一名额，用户永远收不到也不再重试）。被拒时同样 15 分钟退避。

### B3. 保留期提醒通知

出处：`DataRetentionController.swift`

**前提**：设置的清理方式 = **「通知提醒手动清理」**（另一种「自动清理」模式不发通知，
静默删除并写日志）。

> 2026-10-09 修复：此前 `HistoryPersistence` 的 `init` 会无视清理模式，在**每次启动**时
> 静默删掉保留窗口外的全部数据（实测一次启动删了 2 万行），提醒形同虚设。该 init prune
> 已移除——删除只发生在自动清理模式的每日检查点，手动提醒模式绝不删数据。

**调度**：60 秒 Timer 轮询。当「今天已到配置的检查时间」且「今天还没跑过检查点」时执行。

**触发条件**：存在逾期数据（超过保留窗口的行数 > 0）。行数在触发时实时统计，通知里
显示的就是当前真实数字。统计口径为全部 5 张表（含示警记录）——设置 → 存储的
「清除数据 / 范围清理」自 2026-10-09 起同为 5 表口径，提醒计到的行一定清得掉，
清完提醒自然停止。

**重复语义（直接回答「会一直提醒吗」）**：**会——设计如此**。每个检查日到点后若仍有
逾期数据就提醒一次；你不清理也不调大保留天数，第二天到点还会再提醒，直到逾期清零为止
（源码注释原话：*"The reminder repeats daily by design"*）。单日内至多提醒一次
（`lastFiredDay` 标记防重）——但该标记是**内存态**：重启即清零，若重启时已过当天的
检查时间，启动后会立即再查一次，逾期数据还在就会再提醒（2026-10-09 实测：两次重启
各触发一次提醒）。

**两个会提前触发重查的例外**：

- 修改任一存储设置（清理方式 / 保留天数 / 检查时间）→ `rearm()`：重置当日标记并立即
  重查一次。没有这个机制，「检查点跑完之后才把保留期从 360 天改成 2 天」会静默等到
  第二天（2026-09-23 实测后修复）；
- 到点时逾期为 0 → 当天检查点静默消耗（不提醒），次日到点再查。

**送达语义**：被拒时不写任何标记（它的去重本来就靠「每日一次」的时间规则），权限恢复后
下一个检查日照常提醒。

## 四、通知交互：点击导航与动作按钮

出处：`LocalNotification.swift`（category/路由常量 + 注册）、`AppDelegate.swift`
（`userNotificationCenter(_:didReceive:withCompletionHandler:)`）。

### 点击正文 → 跳转

每条系统通知的 `userInfo["route"]` 携带目的地；通知点击（`UNNotificationDefaultActionIdentifier`）
由 AppDelegate 路由：

| 通知 | 目的地 |
| --- | --- |
| 进程流量异常 | 历史窗口，定位到**示警日志** tab |
| 配额阈值（全部档位） | 设置窗口，定位到**配额**页 |
| 保留期提醒 | 设置窗口，定位到**存储**页 |

窗口已打开时只切换 tab 并前置；未打开时懒创建并直接落在目标 tab。设置窗口经
`SettingsTabSelection`、历史窗口经 `HistoryTabSelection`（同一模式）驱动选中态。

### 配额 100% 动作按钮

category `QUOTA_100` 在启动时注册（语言切换时重注册以更新按钮标题），仅挂在 100% 通知上。
三个动作的语义见 B1 小节；动作回调经 `QuotaMonitor.handleQuota100Action(_:)` 写静音/基线
账本，**不触发跳转**；正文点击只跳转，**不改变静音状态**。

## 五、投递公共机制：`LocalNotification.deliver`

出处：`LocalNotification.swift`

所有系统通知都经这一个口：

1. 先查 `getNotificationSettings().authorizationStatus`——`.authorized / .provisional /
   .ephemeral` 放行；`.notDetermined / .denied` 直接拒绝并打日志；
2. 放行后调 `UNUserNotificationCenter.add`，以 `error == nil` 为成功。

**为什么必须先查状态**：实测发现未授权时 `add` 也返回 `error == nil`——只看 `add` 会把
「用户根本收不到」误判为投递成功，导致配额阈值被标成已发、永不再试。这个口子把
「成功 = 系统真的收下了」变成所有调用方共享的保证。

## 六、常见问题速查

**Q：点了启动弹窗的「不再提醒」，就再也收不到任何提醒了吗？**
A：不是。它只永久关闭 A1 这一个启动弹窗。设置面板的内嵌警告（A2）照常显示；三类系统
通知（B1/B2/B3）只要功能开着、权限给了，照样发。

**Q：把通知权限在系统设置里关掉（或首次弹授权时拒绝），会怎样？**
A：三类系统通知全部发不出去（deliver 拒绝），但功能本身照常运行、数据照常落库：
配额阈值会在权限恢复后 15 分钟内补发；进程示警同样 15 分钟退避补发；保留期提醒在
下一个检查日重试。同时 A1 启动弹窗（若未永久关闭）和 A2 面板警告会持续引导你去开权限。

**Q：关掉某个功能开关后，已经排队的通知还在吗？**
A：通知都是即时构造即时投递的，没有排队的定时通知（所有 `trigger` 均为 `nil`）。
关开关 = 对应监视器解除订阅 / 直接短路，之后不会再产生新通知。

**Q：「清除数据」会影响哪些提醒状态？**
A：`QuotaMonitor.resetFiredKeys()` 清空全部阈值 key（本周期已弹过的 80%/100% 会重新
可弹），**同时清空 100% 的增长基线与两个静音标记**；`ProcessAlertMonitor.reset()` 清空
内存累计与退避表，但示警去重主要靠数据库唯一索引——`process_alert` 表本身会被清空，
所以进程示警的「今日已告警」标记也会重置；保留期提醒不受影响（它只看实时逾期行数）。

**Q：为什么启动后不立即检查配额阈值？**
A：`shouldFire` 是跨越式规则，启动后第一次观察只建立基线。这是防误报：应用中午启动时
用量早已过 80%，如果立刻对比 0%，会弹一条「刚刚到达 80%」的假通知。
